# 2026-07-31 — D14, the sweep that cost more than the geometry

D14 is closed, and not by either of the two routes it named. The sweep is still
`Decompose()`; what changed is when it is asked. Unioning the cells in a tree and
sweeping each pair as it is made keeps the component count at two for every call,
whatever the tool's size, so the helper that was 99% of the run becomes
proportional to the mesh it is handed.

## The cost is components x mesh, and only the first factor was ours to move

`Decompose()` materialises one `Manifold` — with its own mesh, and a
`numVert`-sized index vector — per connected component. `unionCells` handed it
one union of every cell in the tool, and a tool carries one volumeless shell per
cell contact, so the component count was proportional to creases x tessellation
over a mesh that was itself growing. That product is the whole of D14.

A pair of cells can leave only the one shell between its two members. So:

```cpp
while (cells.size() > 1) {
  for (size_t i = 0; i + 1 < cells.size(); i += 2)
    merged.push_back(dropVolumelessParts(cells[i] + cells[i + 1]));
  if (cells.size() % 2) merged.push_back(cells.back());
  cells.swap(merged);
}
```

Every call to the sweep sees two components, and `Decompose()` on a two-component
mesh costs two passes over that mesh rather than a thousand.

## Measured

An N x N grid of `r = 3` bosses on a plate, `fillet_tool(r = 1)`, `$fn = 32`.
Wall clock and peak RSS, same machine, same model, before and after:

| bosses | 4 | 9 | 16 | 36 | 64 | 100 |
|---|---|---|---|---|---|---|
| before, s | 1.32 | 0.53 | 1.25 | 5.01 | 24.22 | **111.99** |
| after, s | 0.77 | 0.62 | 1.08 | 2.55 | 4.64 | **7.76** |
| before, GB | 0.16 | 0.34 | 0.66 | 1.69 | 15.24 | **17.23** |
| after, GB | 0.10 | 0.18 | 0.31 | 0.73 | 1.47 | **2.50** |

Linear in the boss count from 16 up: 36 to 64 bosses is 1.8x the bosses for 1.8x
the time and 2.0x the memory, and 64 to 100 is 1.6x for 1.7x and 1.7x. The 100
boss model now costs a third of what 36 bosses cost before, which is the
acceptance D14 asked for.

Tessellation, 36 bosses, `$fn` doubling:

| `$fn` | 16 | 32 | 64 |
|---|---|---|---|
| before | 0.51 s / 0.58 GB | 4.97 / 1.64 | 85.04 / 17.26 |
| after | 0.61 s / 0.19 GB | 2.54 / 0.75 | 10.85 / 2.95 |

Each doubling now costs about 4x, and that is the mesh: stations and facets both
double, so the tool's triangle count is quadratic in `$fn` whatever is done here.
Before, `$fn = 64` cost 17x its `$fn = 32` run.

`chamfer_tool(t = 1)` on the same grid does not regress: 100 bosses is 0.77 s /
0.55 GB before and 0.78 s / 0.20 GB after.

## The result is the same solid, and not the same triangles

Volumes agree to 1e-14 relative on every grid checked, and every one of the 21
regression baselines and all 1175 unit assertions pass. The exported meshes are
not byte-identical: a tree of pairwise unions triangulates a little differently
from one `BatchBoolean` over all the cells — 10530 triangles against 10620 on the
16-boss grid, 7154 against 7096 at `$fn = 16`, both for the same volume. Nothing
downstream reads a triangle count, and the baselines are geometric.

## The union-find route was built and is rejected — do not rebuild it

D14's second bullet was to answer the component question in one pass — union-find
over `MeshGL64` with each component's signed volume from the divergence theorem —
and to rebuild the mesh from the triangles that survive. It was implemented end
to end. The labelling half is exactly right: on every case measured it produced
the same components with the same volumes as `Decompose()`, to the last digit.

**The rebuild is what kills it.** `Manifold(MeshGL64)` is not a copy: the
constructor runs `CleanupTopology`, `RemoveDegenerates` and `SortGeometry` on
whatever it is given. On these tool solids that is destructive, and it is
destructive on the way in, not because anything was dropped — round-tripping an
untouched mesh through `GetMeshGL64()` and back loses volume by itself:

| | volume | tris | verts |
|---|---|---|---|
| the union | 212.283 | 1490 | 895 |
| the same mesh, round-tripped | **212.272** | 1486 | 891 |

11 parts in 212000 is not rounding, and the collapsed edges are far shorter than
that: the baseline tolerance here is `1e-12` of the bounding box. What the
constructor is really doing is resolving the self-touching sheets these solids
carry — the four-face edges R3 measures — and it resolves them differently from
however they arrived. Four unit assertions fail on the result, two of them genus
checks that go from 1 to 2: the round trip opens a hole.

So a Manifold cannot be taken apart and put back together through its own mesh
format without the geometry moving. Anything that needs a component removed must
do it inside Manifold, which means `Decompose()`, which is why the fix is about
calling it on a small component count rather than about replacing it.

Also struck, from D13's log and re-confirmed here: D14's first bullet claims a
`kCanalOverlap` constant already runs canal cells past their station so they
share a slab rather than a face. No such constant exists in the file and none
ever did.

## Left where it was

- `unionCells` still returns a lone cell without sweeping it, which is R9's
  second bullet. A single cell has no contact and so no shell; the inconsistency
  is now visibly harmless rather than merely harmless.
- The reassembly `BatchBoolean` at the end of `dropVolumelessParts` is now nearly
  unreachable — with two components in and one dropped, the single-part return
  fires. R9's note about it can stay as written.
- Three `export-svg ... arcs01` tests fail on this machine, at this commit and at
  its parent, and have nothing to do with the fillet code.
