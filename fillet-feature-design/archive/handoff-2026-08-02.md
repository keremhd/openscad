## READ THIS FIRST — five traps that have each cost hours

1. **Builds are silently discarded in this environment**, and `make` reports
   "Built target" for binaries that do not exist. **Verify the binary's mtime is
   newer than your last source edit before trusting any measurement.** One agent's
   entire report was invalidated by this — its `RESULTS.md` was measured against
   source it had already edited past, and it produced a plausible, wrong baseline
   (1860 assertions / 84 cases) that then propagated into three later briefs. If
   builds misbehave, retry with `dangerouslyDisableSandbox`.
2. **The verified unit-suite baseline is `1688 assertions / 83 cases`.** Any figure
   of 1860/84 in an older document came from the stale binary above.
3. **This machine's locale uses comma decimals**, so `atof`/`strtod` on a decimal
   string silently yields 0. One env var was silently parsing `0.1` as `0` and
   landing in a third, broken mode.
4. **Two of the control numbers are not traceable, and one control is
   nondeterministic.** The figures 19468.9342 / 20489.7290 / 906.7936 are quoted
   throughout this effort as byte-identity controls, but an agent that went looking
   could not tie them to any model definition in the repo or scratch — they came from
   an earlier agent's own SCAD. Prefer defining your own control models and requiring
   exact **base-vs-fix** reproduction over matching those literals. Separately, the
   baseline binary is **byte-nondeterministic on hole-in-a-flat-plate** across
   repeated runs (identical volume 14857.3025669748, differing vertex order), so
   check for that before reporting a vertex-order difference as a regression.
5. **Brushes are NOT a named `brush =` argument.** That is a parse error, and it
   appears throughout `handoff-2026-08-01.md`. Brushes are children 1+ of the tool,
   and the tools emit the *tool solid*, so the target must be differenced (round)
   or unioned (fillet) by hand. Correct form:

   ```openscad
   difference() { thing(); round_tool(r = 2) { thing(); brush_shape(); } }
   union()      { thing(); fillet_tool(r = 2) { thing(); brush_shape(); } }
   ```

## The single most important methodological lesson from this session

**A recorded measurement closed a defect, and the measurement was wrong.**

D18 was closed on the control "dropping only the sagitta term gives 5.73 / 3.74 /
1.87, converging below the 3.62 flat-wall control". A fresh harness measures
**172.51 / 176.26 / 178.13** for the same change. The harness is credible because it
reproduces *every other figure in the record digit-for-digit* — shipping tee
12.62 / 10.12 / 9.84, boss-on-plate 3.62 and 19468.9342, rounded cube 906.7936,
crossing pipes 20489.7290, oblique genus −13 and +39.

The tell: **5.73 / 3.74 / 1.87 sit exactly at or below the facet angles
7.5 / 3.75 / 1.875** at those tessellations. A radius-based crease classifier run on
*shipping* returns 4.61 at `$fn`=48 — it cannot see the 12.62° defect the record
itself reports. It was a classifier saturated at the tessellation floor.

**Consequence for any crease measurement**: classify a triangle as "wall" only when
it lies in one of the *unfilleted model's own facet planes* (to ~1e-9). Testing
against an analytic radius is wrong by `R(1−cos(π/fn))`, which is the same order as
the defect being measured. Before trusting any metric, check what it returns on a
case whose answer is already known.

# D17.3 — the brushed corner — SOLVED, two blockers under repair

This is the main result of the session and the closest thing to landable work.

## The mechanism, fully diagnosed

Three separate causes were found and separated:

1. **Truncation is skipped at brush-marked vertices.** `chainJunctions`
   (`FilletBuilder.cc:1861`) drops every vertex in `noCorner`, and truncation only
   happens at a `Junction`. So the ball rolls a full radius past the wall that
   should stop it, and since the tool is one global `wedge - canal`
   (`FilletBuilder.cc:2621-2625`), the canal built from those *illegal* ball
   positions gouges the neighbouring chain's bead — a 2.9 mm hole that survives to
   `$fn`=128.
2. **The corner is left empty** because each bead is `wedge − canal` and the canal's
   last ball position carves a spherical scoop into the bead's end. Under global
   subtraction the neighbour's wedge fills that scoop; under per-chain both beads
   keep their own, so their union leaves an r-deep open notch.
3. **The oblique pinch.** A bead's cross-section is tangent to its own wall at
   height r, and *that wall is the one the other bead's crease ends on*, so the two
   tangency lines converge on the same point of the sharp vertical edge **however
   far back either bead stops**. Stopping short can never separate them; only
   overlapping can. This is why capping the bead ends was a measured no-op.

## The design the owner specified

The owner's principle, which is what the fix implements:

> **Does an original crease of the model leave the vertex still sharp?** If it does,
> the two beads must meet in a **seam that lines up with that edge** — a crease line
> on a concave tool, a bump line on a convex one. A ball can never line up with a
> sharp edge; it rounds across it. If nothing sharp leaves the vertex, there is
> nothing to line up with and a corner ball is correct.

It does not matter *why* a crease went unfilleted — brush, size gate, or
feature-angle filter are treated identically. What matters is that it is still a
sharp edge in the output.

The owner also framed the baseline: **each fillet edge is treated independently and
the beads connect**; the corner sphere is an *enhancement* for the no-brush case, not
a structural requirement. Omitting it is always a safe fallback.

## The implementation — two layers

Both in `src/geometry/fillet/FilletBuilder.cc` inside `buildRoundSolid`.

**Layer 1 — local grouping.** Env-gated `OPENSCAD_FILLET_LOCALGROUP=1`.
- `creaseLeavesUnfilleted(m, adj, filleted, thresholdDeg, v)` — an edge at `v`
  counts as a model crease iff `isFeatureAngle(dihedral, thresholdDeg)`, using the
  same threshold the selection uses. This is what keeps tessellation seams on curved
  walls out, honouring standard 5. If any such crease is not in the filleted set,
  `v` is a **seam vertex**.
- Chains grouped by **union-find**, linked at every junction that actually builds a
  corner ball. Seam vertices build no ball, so their chains stay unlinked and take
  **per-chain** canal subtraction; everywhere else all chains at the vertex land in
  one group and take the existing **global** subtraction unchanged.
- Corner cell and ball suppressed at seam vertices.
- It degenerates to today's code exactly where a ball is built, which is why the
  planar controls come out byte-identical.

**Layer 2 — the seam overrun.** `seamOver` = 0.10·r by default when LOCALGROUP is
set. Junctions at seam vertices are skipped in `junctionAt` while `seamOver > 0`, and
in the "stop a hair short" block the sign is flipped so `lerpSection` **extrapolates**
the end section *past* the vertex. The two beads then overlap and their surfaces
cross transversally instead of grazing.

## Two confirmed blockers, currently being repaired

**Blocker 1 — the overrun silently moves every brush boundary on the chain.**
`FilletBuilder.cc:2481-2484`, the `if (back > 0.0)` guard on the `sectionAt` update.
Moving `sec[endIdx]` past the vertex without updating `sectionAt[ci][endIdx]`
desynchronises index space from chain-parameter space for the whole last segment —
and on a straight polyhedral crease a chain has only **two** stations, so that is the
entire bead. Measured: a brush asking for `[0,4]` and `[8,12]` of a 20 mm edge
delivers `[0,3.84]` and `[7.88,11.92]`. Displacement is exactly `0.1·r·(1 − x/L)`,
worst case 0.10·r = 0.3 mm at r=3. At c=0 the shortfall is exactly 0.00000.
It also degrades quality: on the corner-brush case, layer-1-only is 0.0006 mm³ proud
of the hand ideal and layer 1+2 is 0.0221 — **37× worse**, and that 0.0221 is
precisely the bead the brush asked for and did not get.
The code comment ("the overrun is a repair of the bead's end, not new length the
caller's brush ever selected") is the bug, not a justification: it does not append
length, it **re-parameterises the segment**.

**Blocker 2 — the overrun is not free on a thin wall.** `FilletBuilder.cc:2470-2475`.
With a 0.2 mm wall and `fillet_tool(r=3)`, the bead runs through and stands
**0.1 mm proud on the outside of the part** — 0.39130 mm³ on a face nothing was
blending. Condition is simply `wall thickness < 0.10·r`, ordinary at large radii.
Untested siblings from the same mechanism: a wall that **turns** or **ends** within
0.10·r of the vertex.

suppression is not gated on `seamOver` while the junction skip is, giving a third

## Why global subtraction exists at all

Recorded at `FilletBuilder.cc:2615-2619` and in `log-2026-07-28-m8.md`. Per-chain was
the shipping behaviour at M7 and was reverted at M8 for two reasons: **sufficiency**
(after spine truncation the canal is exactly the set of legal ball positions, so
cross-chain cutting is harmless) and **necessity** (the corner ball must cut the
wedges of *all three* chains meeting at a cube corner).

Both halves are narrower than they read. Necessity is about the **corner ball**, and
it is written in terms of **three** chains — at a two-chain junction there is no
third wedge to reach into. Sufficiency is a permission, not a requirement. This is
why local grouping satisfies the recorded rationale rather than overturning it.

Note the M7 "clover cube" damage was measured against an **untruncated** canal, so it
is not evidence against per-chain today.

# D19 — the subtractive scalloped ledge — characterised, unfixed

`round_tool` on a curved wall stops **short** of the wall and leaves un-cut original
surface standing as a ragged ledge. No bump; the fault is an under-cut.

- Worst case **1.526 mm = 0.76 r** (Ra=10, Rb=5, r=2, `$fn`=96). Other configs:
  20/5/2 → 0.26 r; 40/5/2 → 0.25 r; 20/10/2 → 0.35 r; 10/5/0.5 → 0.55 r.
- **Plateaus**, does not converge: 1.7934 / 1.6331 / 1.5261 / 1.4665 / 1.4347 at
  `$fn` 24/48/96/192/384, increments halving to a non-zero limit ≈ 1.40 mm. The flat
  control converges as 1/`$fn`²: 0.0857 / 0.0220 / 0.0064 / 0.0024.
- **Mechanism**: the ball is seated against the **tangent plane at the crease**.
  `makeRoundSection` puts the centre at `C = v + dir·(r/cos(φ/2))·bis` using averaged
  normals (`FilletBuilder.cc:1655`). On a convex wall of radius R the wall falls away
  from that plane, leaving `δ ≈ r²tan²(φ/2)/2R`. Measured from the built ball's own
  position: 1.038 / 0.907 / 0.829 / 0.793 / 0.775 converging to ≈0.757 against a
  prediction of 0.7178 — 5 % agreement, tessellation-independent.
- **It is NOT fixable by fixing D18.** D18 is the *overshoot*; D19 is the *seating*,
  which D18's own controls explicitly ruled out as D18's cause. Worse, the lever for
  D19 is the shelved facet-plane seating solver, whose recorded blocker was "convex
  `round_tool` regresses — the subtracted tool needs the overshoot that seating
  collapses". **A and D18 are coupled through the same code with opposite
  requirements.**

# D20 — the fins — NEW, fix in progress

The rounded band's **inner** rim, where it meets the bore, is a **ruffle of
overlapping lobes that fold over one another**, leaving knife-thin tabs of un-cut
bore wall hanging into the hole. Distinct from D19 and worse at most facet phases.

- **1.02 mm (0.51 r)** at `$fn`=96 r=2, but `$fn`=96 is a *lucky phase* — rotating
  the hole by less than one facet gives **1.85 mm (0.93 r)**. `$fn` 96/97/98/100/128
  → 1.02 / 1.78 / 1.70 / 0.98 / 0.89.
- **Plateaus**: ~4 % of band edges stay as folds sharper than 20°, up to 180°, at
  every tessellation from 24 to 384. A correct rolling-ball round has **no** convex
  edge inside the band; the flat control's sharpest internal edge is exactly
  `360/$fn` and halves every step.
- **NOT a curvature problem — it is crease-polyline regularity.** Decisive control:
  same sphere, same bore, same r, same `$fn` — bore **along** the axis (crease is a
  regular 96-gon) gives **0 folds >20°**; bore **across** the axis gives **327 folds
  >20°, up to 176°**. On the pipe the shortest crease segment is **0.0014 mm against
  a 0.33 median**, and that ratio worsens as 1/`$fn`².
  **Therefore cylinder detection would not fix it.** The lever is resampling the
  crease polyline, which needs no curvature inference.
- **Not cosmetic**: Manifold gives **genus 1 at `$fn`=384**; CGAL gives
  **`Simple: no` at `$fn`=192** while the unrounded model at 192 is `Simple: yes`.
- Affected: cross-drilling a round bar/pipe/tube, holes through cones, off-axis holes
  in spheres. Unaffected: flat plates, anything concentric with a body of revolution,
  concave insides of bores.

## D20 crease resampling — round 1 done, round 2 IN FLIGHT

**Round 1 confirmed the idea and identified what blocks it.** Worktree
`agent-a738a6349f9e6b7db`, `FilletBuilder.cc` +142/−10, `FilletBuilder_internal.h` +81.
`resampleChains()` runs right after `buildChains()`, before sections are placed.
Trigger `kSliverFraction = 0.5` (resample only if a segment is under half the chain's
own median — strictly below 1, so a regular crease is never touched); stride
`kResampleStride = 1.5` medians, taking the *nearer* of the two bracketing vertices.
The crease itself is never moved: dropped vertices stay in `Chain::raw` with
`Chain::station` mapping into it, and `chainNormals` / `chainContacts` average each
wall over the whole raw stretch a station stands for, length-weighted, reducing
exactly to the prior expressions when nothing is dropped.

Achieved: fold census **0 % at `$fn` 48/96/192 across all four curved-wall families**,
and **flat across facet phase** — at `$fn`=96 rotated 0/0.5/1/1.875/2.5/3.75° and at
`$fn` 97/98/100/128, HEAD gives 171–760 folds and the fix gives **0 at every one**.
Repaired `hp_fn384` genus 1 → 0, `sph_across_fn384` genus −6 → 1, and CGAL `hp_fn192`
`Simple: no` → `Simple: yes`. Suite 1688/83 green. Performance +0.3 %. A ring-wide
ruffle of 16 fold clusters at `$fn`384 became 4 isolated spots.

Blocked on: `hp_fn96_rot0.5` genus 0 → **−1**; `cone_fn96` still −1; `$fn` 24 and 384
retain a residue; and the **D19 ledge worsens, 1.78 mm (0.76 r) → 2.05 (0.89 r)**.

**The binding constraint, and the round-2 task.** Stations must currently be a
**subset of existing mesh vertices**, because `Chain::verts` holds mesh indices that
junction identification and the brush's bookkeeping depend on. So regularity can only
be bought by *deleting* stations — paying in sampling density — and the builder lofts
straight chords between stations, so longer chords dip further from the true wall.
That is both the deeper ledge and the sporadic self-intersections. At `$fn`=24 the
crease is already at minimum density, so no stride value from 1.0 to 3.0 clears it.

Two pieces of evidence that the constraint binds rather than the idea failing:
residuals are **non-monotone in the stride** (88 / 338 / 0 / 6 folds at 1.25 / 1.5 /
2.0 / 3.0 — discrete events, not a smooth conditioning problem), and **uniform-arc
placement snapped to the nearest vertex was worse** (46 folds vs 2), which is what
snapping-destroys-uniformity predicts.

## D20 round 2 — done, does not ship, and it VOIDS round 1's numbers

Worktree `agent-a1cc15393bdb9006e`; `work/NOTES.md` is the record, `results.csv` the
data. **Read the measurement warning below before using any round-1 figure.**

**What was built.** `Chain` now carries two polylines: `raw` (the crease exactly as the
mesh has it, never altered) and a station list of `at` (raw parameter), `pts`
(position) and `verts` (mesh vertex, or **−1** where interpolated). Empty `at`/`pts` is
the identity, so an unresampled chain feeds bit-identical inputs downstream.
`resampleChains` places **`segments` stations at equal arc length — the same count the
crease has, so density is preserved exactly**; round 1's stride is gone. Ends stay
exact mesh vertices. `chainNormals` length-weights each wall over the raw arc a station
spans, with a fast path leaving the unresampled case bit-for-bit unchanged.

**The designated risk was not the hard part.** Resampling runs strictly *before*
`chainSelection`, so there is still exactly one chain-parameter space and it is the one
the brush cut — `sectionAt`, `toSectionSpace`, `keep` and `noCorner` needed no change.
**The real hazard was found by reading**: `checkChainSizes` built its junction-membership
set from `chain.verts`, so a `-1` would have made *every pair of resampled chains*
falsely appear to meet and skip the crowding test. Fixed by using `chain.raw`. Anyone
touching `Chain::verts` should look for other consumers that assume it holds real
vertex indices.

**Result: does not ship.** It achieves what it was aimed at — **0 folds at `$fn`
48/96/192 on pipe, sphere and cone**, sharpest band edge 3.9° against a 3.75° facet
angle, and it repairs genus the baseline gets *wrong* (sphere −3 → 1 at `$fn` 24 and
48). But at rotated facet phases it leaves four ~1e-5 mm³ **needle tetrahedra**
(genus −1 at rot0.5 and rot1, confirmed as disconnected components). Root cause
established: cells are hulled between consecutive stations, so a chord can span a raw
vertex and pass inside it. A per-station crease slack was tried, measured, found to
trade the crumb for a spurious tunnel and regress the sphere, and **reverted** — tree,
binary and results verified consistent afterwards by re-running three rows.

**Measured**: the fold census above, suite **1688/83 three times with no failures**,
the collar sweep, the component diagnosis. **Assumed and NOT measured**: the D19 ledge,
`$fn`=384, six of the ten facet phases, CGAL validity, control byte-identity, timing,
renders.

**Next step, and it is cheap**: measure the **D19 ledge**. Round 2 preserves the
station count exactly, so it should be no worse than HEAD's 1.78 mm. That single number
is the direct read on whether the density argument holds, and it decides whether this
approach is worth pushing through the needle-tetrahedron problem or abandoning.

### MEASUREMENT WARNING — round 1's D20 numbers are void until re-measured

The crease threshold is `1.5 × max($fa, 360/$fn)`, and **`$fa` defaults to 12**. A model
that sets only `$fn` is therefore measured through an **18° threshold that cannot see
its own tessellation**, however fine `$fn` is. Confirmed: setting `$fa = 360/$fn` and
`$fs = 0.01` moved the threshold from 18.0° to 5.6° at `$fn`=96.

Round 1's headline — "fold census 0 % at `$fn` 48/96/192 across four families, flat
across ten facet phases" — **is flat in `$fn`, which is exactly what that artefact
produces.** Round 1's models were not opened (read-only worktree), so this is inference
rather than proof, but **treat those numbers as void until re-measured with
`$fa = 360/$fn`.** Round 1 also used a 3 mm wall against r=2, so every crease was
refused for size and nothing was built.

This is the **second** time in this effort a result has rested on a metric that could
not see what it claimed to measure — the first being D18's saturated crease classifier.
A sibling trap was hit here too: **a radius that does not fit is warned about, skipped,
and still exports a plausible mesh**, so an export succeeding proves nothing.
